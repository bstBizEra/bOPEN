# ADR-0014 — Server-side sessions with one active tenant context, latest wins

**Status:** Proposed
**Date:** 2026-07-29
**Owner:** Architecture Authority
**Plan alias:** `ADR-P2-005` (BOPEN-IDP-001 §20)
**Phase:** Phase 2 — Membership & Enterprise Onboarding

## Context

A Principal with relationships in several tenants must switch tenant without
re-authenticating, while every authorization input is revalidated. Separately, revocation
must actually take effect — a token that outlives the relationship it represents is the
residual-access risk the phase exists to close.

## Decision drivers

- Authentication lifetime and tenant-context lifetime are different concerns.
- Revocation must not wait for a long-lived token to expire.
- A context must never carry authorization data from the tenant it replaced.
- Stateless tokens cannot be revoked; stateful lookups on every request cost latency.

## Options considered

1. **Long-lived stateless tenant tokens.** Cheapest to verify; revocation is impossible
   within the token lifetime. Rejected — defeats the leaver control.
2. **Opaque tokens with a store lookup on every request.** Instant revocation, highest
   per-request cost and a hard availability dependency on the store. Rejected for Phase 2.
3. **Short-lived signed context tokens over a revocable server-side session.** Bounded
   residual access, no per-request store hit, revocation effective within one token
   lifetime. Selected.
4. **Multiple simultaneous active contexts per session.** Convenient for multi-tenant
   dashboards; multiplies the revocation surface and confuses "current tenant". Deferred.

## Decision

Adopt option 3.

- Two distinct artifacts: an **authentication session** (not tenant-bound, server-side,
  revocable) and a **context access token** (tenant-bound, short-lived, signed).
- Context token lifetime is **5 minutes**; clock-skew allowance is at most 60 seconds
  (D-P2-006).
- **One active context per session. The latest context supersedes the previous one**
  (D-P2-008). Option 4 remains open for a later ADR if a product need is demonstrated.
- On every switch the service revalidates the session, client binding, tenant selector,
  membership (or delegated grant), and **derives roles and scopes fresh from target-tenant
  state**. Nothing is copied from the prior context.
- Header values (`X-Tenant-ID`, `X-Context-ID`) are untrusted selectors. A header/body
  mismatch is a denial. A stale `expected_context_id` is a conflict.
- Revocation propagation objective (D-P2-014): **new issuance denied immediately**; active
  contexts invalidated within one token lifetime. Non-active membership transitions and
  grant revocations record an invalidation obligation which the context store discharges.
- Any failure in the switch algorithm returns **no token**.

## Consequences

- Worst-case residual access after revocation is bounded by the 5-minute token lifetime plus
  skew. This is the number to quote in security review; it is a deliberate ceiling, not an
  accident.
- Shortening the lifetime increases switch traffic; 5 minutes is the recommended default and
  is configurable per deployment, not per tenant.
- The session and context stores are in-memory adapters in Phase 2. A durable, replicated
  store is required before any deployment — **outstanding work, not closed by this ADR**.
- Multi-tenant UIs must switch context rather than hold two tenants open at once.

## Security/data implications

- Bounds the stale-access-after-deprovision threat (BOPEN-IDP-001 §16).
- Prevents cross-tenant privilege carry-over by construction (INV-P2-010).
- Session identifiers are credentials: never logged, never placed in audit metadata.
- Obligation records are the audit trail proving invalidation was required and discharged.

- `platform_kernel/context_service.py` — `ContextSwitchService`, `InMemorySessionStore`.
- `tests/unit/test_context_switch.py` — `P2-T024` role isolation, `P2-T028` revocation,
