# ADR-0010 — Enterprise SSO broker runs behind an adapter port

**Status:** Proposed
**Date:** 2026-07-29
**Owner:** Architecture Authority
**Plan alias:** `ADR-P2-001` (BOPEN-IDP-001 §20, BOPEN-P2-001 §12.2)
**Phase:** Phase 2 — Membership & Enterprise Onboarding

## Context

Phase 2 must accept enterprise SAML 2.0 and OpenID Connect authentication and SCIM 2.0
directory synchronisation. DEC-0003 already selected BoxyHQ Jackson (now Ory Polis) as the
protocol broker. What remains undecided is *where the boundary sits*: whether bOPEN code
depends on the broker directly, and what the kernel is permitted to trust from it.

## Decision drivers

- The kernel must remain the source of truth for principals, memberships, roles and scopes.
- Protocol termination is commodity work with a large, security-sensitive surface.
- Broker outage must not degrade into a local authorization decision.
- Tests must run offline with no broker and no network (BOPEN-P2-001 §12.6).
- A floating dependency version is prohibited (BOPEN-P2-001 §12.2).

## Options considered

1. **Implement SAML and OIDC natively in bOPEN.** Maximum control; large cryptographic
   attack surface owned by us; slowest to a correct implementation. Rejected.
2. **Embed the broker as an in-process library.** Fewer moving parts, but couples kernel
   deployment to broker release cadence and puts broker types in kernel code. Rejected.
3. **Run the broker as a separate service reached only through a bOPEN-owned port.**
   Kernel imports no broker types; the adapter is the single translation point. Selected.
4. **Use a hosted SaaS identity broker.** Removes operational burden but places tenant
   identity data with a third party ahead of a data-residency decision. Rejected for
   Phase 2; may be revisited when residency is decided.

## Decision

Adopt option 3.

- The broker is deployed as a **separate self-hosted service**. bOPEN reaches it only
  through `BrokerPort` (`platform_kernel/idp_bridge.py`).
- No bOPEN module outside the adapter may import broker types, call broker APIs directly,
  or persist broker-native identifiers as bOPEN primary keys.
- The broker **normalises protocol messages**; it does not decide authorization. Inbound
  roles and groups are inputs to a versioned bOPEN mapping, never grants.
- The exact broker distribution, release version, image digest, database, API
  authentication method, callback URLs, SAML audience, OIDC path and SCIM path are pinned
  in the **environment contract**, not in application code. `latest` is prohibited.
- Broker unavailability produces a typed `DEPENDENCY_UNAVAILABLE` failure. It must never
  produce a local allow.

## Consequences

- The bridge is testable with a deterministic fake port; the Phase 2 suite runs with no
  network access.
- Swapping brokers is an adapter-level change, not a kernel change.
- An environment contract artifact is now **required** and does not yet exist. Until it is
  authored, D-P2-001 (exact broker version and digest) remains open; this ADR fixes the
  boundary, not the release.
- Operational cost: one more service to deploy, monitor and patch.

## Security/data implications

- Broker administration APIs are a privileged surface and must not be reachable from tenant
  networks.
- The adapter must authenticate the broker on every inbound event; `StaticBrokerPort` in the
  test adapter is a stand-in for that check, not an implementation of it.
- Raw assertions, authorization codes and broker bearer tokens must never cross the adapter
  boundary into kernel state or audit evidence.

## Evidence

- `services/platform-kernel/python/platform_kernel/idp_bridge.py` — `BrokerPort`, `IdpBridge`.
- `tests/unit/test_idp_bridge.py` — offline conformance and `DEPENDENCY_UNAVAILABLE` path.
- BOPEN-IDP-001 §7 (trust boundaries), BOPEN-P2-001 §7.1 (ownership table).

## Supersedes / superseded by

Refines DEC-0003 for the Phase 2 boundary. Supersedes nothing.
