# ADR-0016 — SCIM ordering uses a tombstone barrier; deprovision never deletes

**Status:** Proposed
**Date:** 2026-07-29
**Owner:** Engineering Authority
**Plan alias:** `ADR-P2-007` (BOPEN-IDP-001 §20)
**Phase:** Phase 2 — Membership & Enterprise Onboarding

## Context

SCIM directories deliver events at least once and not always in order. The dangerous case is
specific: a leaver is deprovisioned, then a stale in-flight profile update arrives carrying
`active: true` and silently restores their access. This is the joiner-mover-leaver control
failing in the direction that matters.

## Decision drivers

- Deprovision must win against any concurrent or late-arriving update.
- Replayed events must not create duplicate Principals or Memberships.
- Not every provider supplies a usable version or sequence field.
- Audit-relevant identity records must survive deletion for non-reassignment.

## Options considered

1. **Last write wins.** Trivial, and directly produces the leaver-reactivation failure.
   Rejected.
2. **Provider version comparison only.** Correct where the provider supplies `meta.version`
   or a sequence; silently degrades to option 1 where it does not. Insufficient alone.
3. **Provider sequence plus a monotonic deprovision tombstone barrier.** Selected.
4. **Full event-sourced reconciliation of directory state.** Strongest, and disproportionate
   to Phase 2 scope. Deferred.

## Decision

Adopt option 3.

- Each `(directory_id, resource_id)` tracks the **highest observed sequence**. An event with
  a lower sequence is rejected with `SCIM_ORDERING_CONFLICT`.
- A deprovision writes a **tombstone at its sequence**. Any non-deprovision event at or below
  that sequence is rejected — a stale update can never reactivate a later-deprovisioned
  relationship, even if it arrives with a plausible sequence.
- **Deprovision has priority over profile updates.** Where both are pending, deprovision
  applies.
- **Idempotency**: a replayed `event_id` returns the prior logical outcome. A second create
  for an already-mapped directory resource returns the existing mapping rather than creating
  a second Principal. Conflicting reuse of an `externalId` within a directory is rejected and
  audited.
- **Deprovision maps to a membership state through per-directory policy**, defaulting to
  `suspended`, with `revoked` available where the tenant requires it (D-P2-009). **Hard
  deletion of audit-relevant identity records is prohibited** — there is no configuration
  that enables it.
- Every state change runs through the ADR-0013 state machine. The bridge never writes
  membership state directly.

## Consequences

- A provider that supplies no sequence degrades to replay-safety without ordering safety.
  Such directories must be identified during onboarding and accepted as a named risk;
  detecting and reporting them is outstanding work.
- Tombstones grow monotonically per directory resource. They are small; a retention rule
  belongs to ADR-0019.
- A legitimate rehire is a **new membership**, not a reactivation, consistent with ADR-0013.
- Recovery from an erroneous deprovision is an explicit administrative reinstatement, which
  is audited — deliberately not automatic.

## Security/data implications

- Closes INV-P2-014, the highest-severity SCIM failure mode.
- Prevents duplicate-identity creation via replay (INV-P2-013).
- Directory-to-tenant binding is validated on every event; tenant is never inferred from an
  email domain.

## Evidence

- `platform_kernel/idp_bridge.py` — `_guard_ordering`, `deprovision_tombstones`,
  `resource_principal`, `external_id_binding`.
- `tests/unit/test_idp_bridge.py` — `P2-T047` replay, `P2-T048` deprovision,
  `P2-T049` stale reactivation, out-of-order rejection.
- BOPEN-IDP-001 §10.3; BOPEN-P2-001 §12.5.
