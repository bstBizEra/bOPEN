# ADR-0013 — Membership transitions use contract-driven optimistic concurrency

**Status:** Proposed
**Date:** 2026-07-29
**Owner:** Engineering Authority
**Plan alias:** `ADR-P2-004` (BOPEN-IDP-001 §20)
**Phase:** Phase 2 — Membership & Enterprise Onboarding

## Context

Membership state drives every authorization decision. Transitions arrive concurrently from
tenant administrators, SCIM directories, security controls and expiry schedulers. Two
writers must never both believe they won, and a transition the specification does not
sanction must never occur.

## Decision drivers

- The set of legal transitions must be inspectable and testable as data, not inferred from
  branching code.
- Deprovisioning must not be lost to a race with a profile update.
- Retries from an at-least-once event source must not double-apply.
- Phase 2 persistence is in-memory; the model must survive the move to PostgreSQL unchanged.

## Options considered

1. **Transitions encoded as code branches.** Fastest to write; drifts from the specification
   silently and cannot be exhaustively tested from the contract. Rejected — the plan's own
   risk table names this drift.
2. **Pessimistic row locking.** Correct under contention but couples the domain to a database
   capability the Phase 2 in-memory boundary does not have. Deferred, not rejected: it
   remains available as an implementation of the same contract.
3. **Contract-driven table plus optimistic version compare-and-swap.** Selected.

## Decision

Adopt option 3.

- The legal transition set lives in a **pinned contract file**, loaded and version-checked at
  construction. Any transition absent from it is rejected with `INVALID_TRANSITION`.
- The loader rejects unknown states, actions, actor types, conditions and reason codes, and
  refuses to load a contract in which a terminal state has an outbound transition.
- Every membership carries a **monotonic integer version**. Commands supply the expected
  version; a mismatch is `STALE_VERSION`. At most one competing writer commits.
- Every mutating command supplies an **idempotency key**. The same key with an equivalent
  payload returns the prior receipt; the same key with a different payload is `CONFLICT`.
- The following commit as **one unit of work**: state change, version increment, and the
  context-invalidation obligation record. Obligations are idempotent and retryable.
- Terminal states (`revoked`, `expired`, `left`, `removed`) never reactivate implicitly
  (D-P2-005). A new relationship requires a new membership.
- Transitions return an immutable receipt; denials emit `membership.transition_denied`.

## Consequences

- Allowed and forbidden transitions are both parameterisable directly from the contract,
  which is how 11 allowed and all 31 absent ordered pairs are covered today.
- Adding a transition is a contract change under review, not a code edit — the intended
  friction.
- Optimistic concurrency means a losing writer retries. Under heavy contention on one
  membership this is less efficient than a lock; that trade is accepted because contention
  on a single membership row is rare and correctness is unaffected.
- When persistence lands, the version column must map to a database-enforced conditional
  update. Application-level CAS alone is insufficient once there are multiple processes —
  **this is a gap to close in the persistence work package, not in Phase 2.**

## Security/data implications

- Fail-closed: any validation, authorization or condition failure denies and audits.
- Deprovision priority is preserved by the ordering guard in ADR-0016 rather than here.
- The transition contract is security-relevant configuration; changes require review under
  CODEOWNERS for `contracts/`.
