# ADR-0012 — Invitation tokens are high-entropy, peppered-digest, single-use

**Status:** Proposed
**Date:** 2026-07-29
**Owner:** Security Authority
**Plan alias:** `ADR-P2-003` (BOPEN-IDP-001 §20)
**Phase:** Phase 2 — Membership & Enterprise Onboarding

## Context

An invitation token is a bearer credential that converts into tenant membership. It travels
through email, so it is exposed to mail relays, logs and forwarding. The store that holds
its verifier is a high-value target.

## Decision drivers

- A leaked invitation store must not yield usable tokens.
- Acceptance must be single-use even under concurrent redemption.
- Comparison must not leak timing information.
- The scheme must be replaceable without re-hashing existing records or rewriting the engine.

## Options considered

1. **Store the raw token.** Never acceptable. Rejected.
2. **Unkeyed SHA-256 of a 256-bit CSPRNG token.** Cryptographically adequate on its own —
   at 256 bits of entropy an offline preimage search is infeasible, and the slow-hash
   argument that applies to passwords does not apply here. It offers no defence, however, if
   the generator is ever weakened or a token is low-entropy by mistake.
3. **HMAC-SHA256 under a server-held pepper.** Same cost, but a stolen database is useless
   without the pepper, which lives outside the database. Defence in depth against exactly
   the compromise that matters. Selected.
4. **Argon2id / scrypt.** Designed for low-entropy secrets. Adds material CPU cost per
   validation for no gain against 256-bit random tokens. Rejected as miscalibrated.

## Decision

Adopt option 3.

- Raw token: **256 bits from a CSPRNG**, URL-safe, generated server-side.
- Verifier: **`hmac-sha256-v1`** — HMAC-SHA256 keyed by a server pepper held outside the
  application database and outside source control.
- The scheme identifier is persisted on every invitation record, so a future scheme coexists
  with existing records rather than forcing a migration.
- Comparison is constant-time.
- The raw token is returned **exactly once**, at issue, and never persisted, logged,
  audited, placed in an exception message, or included in evidence.
- Acceptance is single-use and atomic with membership activation, guarded by a
  compare-and-swap on the invitation version so exactly one concurrent redemption wins.
- Lifetime is **7 days**, bounded above at 30 days (D-P2-003).
- One open invitation per `(tenant, normalized destination, purpose)` (D-P2-004).
- Unknown, malformed, expired, consumed, declined and tenant-mismatched tokens all return a
  single generic denial that permits no account or tenant enumeration.

## Consequences

- **Implementation delta.** `kernel_core/membership.py` currently ships `Sha256TokenHasher`
  (`sha256-v1`, unkeyed) — option 2. Ratifying this ADR requires adding a peppered hasher
  and a pepper-provisioning path. The change is confined to the `TokenHasher` port and its
  wiring; the engine, contracts and tests are unaffected apart from the scheme identifier.
  This delta is tracked in `docs/evidence/phase-2/provisional-decisions.md`.
- A pepper is now an operational secret requiring provisioning, rotation and backup. Pepper
  rotation invalidates outstanding invitations unless both schemes are accepted during an
  overlap window; recommend accepting the prior scheme for one invitation lifetime.
- Option 2 is **not a vulnerability** if the Authority prefers to defer the pepper; it is a
  weaker posture. Deferral should be recorded as an accepted risk rather than left silent.

## Security/data implications

- `email_normalized` on an invitation is confidential personal data (ADR-0019).
- Enumeration resistance depends on denial messages staying uniform; asserted by test.
- Timing-attack resistance depends on `hmac.compare_digest` remaining in the resolution path.

## Evidence

- `kernel_core/membership.py` — `TokenHasher`, `Sha256TokenHasher`, `InvitationEngine`.
- `tests/unit/test_invitation_engine.py` — `INV-P2-002` non-persistence,
  `P2-T004` single-use, `P2-T005`–`P2-T007` denial uniformity.
- BOPEN-IDP-001 §6.4; BOPEN-P2-001 §9, §21 (D-P2-002, D-P2-003, D-P2-004).
