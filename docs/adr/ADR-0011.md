# ADR-0011 — External identity is keyed on issuer and subject, never on email

**Status:** Proposed
**Date:** 2026-07-29
**Owner:** Security Authority
**Plan alias:** `ADR-P2-002` (BOPEN-IDP-001 §20)
**Phase:** Phase 2 — Membership & Enterprise Onboarding

## Context

One bOPEN Principal may authenticate through several enterprise identity providers, and the
same human may appear in more than one tenant's directory. bOPEN needs a rule for when two
external identities are the same Principal. Getting this wrong is an account-takeover
vulnerability, not a usability defect.

## Decision drivers

- Email addresses are reassignable, spoofable in unsigned attributes, and shared across
  tenants. They are contact data, not identity.
- A provider's stable subject is the only attribute the provider guarantees.
- Silent linking is invisible to the user and therefore unauditable.
- Enterprise onboarding must still be low-friction for legitimate users.

## Options considered

1. **Link on verified email match.** Simplest onboarding. An attacker who controls any IdP
   that asserts a victim's email address takes over the account. Rejected outright.
2. **Link on email match plus domain allowlist per tenant.** Better, but a compromised or
   misconfigured tenant IdP still asserts arbitrary addresses within its own domain, and
   domain hints are configuration, not proof. Rejected.
3. **Link only on an explicit, authenticated act, keyed on `(connection, issuer, subject)`.**
   Selected.

## Decision

Adopt option 3.

- External identity uniqueness is enforced on the canonical triple
  **`(connection_id, issuer, subject)`**. Email never establishes equivalence.
- Linking a new external identity to an existing Principal is permitted by exactly three
  bases, each audited:
  1. an authenticated, active Principal accepts an explicit link challenge;
  2. a valid invitation bound to the same tenant, followed by provider authentication;
  3. a separately authorized administrative recovery procedure with evidence.
- The following are prohibited with no configuration switch to enable them:
  - automatic linking because email strings match;
  - linking across tenants via a domain hint;
  - overwriting an existing external identity binding;
  - reassigning a stable `(issuer, subject)` to a different Principal.
- An unrecognised subject arriving at a callback is a **denial** (`IDENTITY_LINK_DENIED`),
  not an implicit registration. Just-in-time provisioning, where enabled, runs through the
  invitation path so a bOPEN-side record authorizes it.
- `email_snapshot` may be stored as non-authoritative contact/display data only.

## Consequences

- First enterprise login for a new user requires an invitation or an explicit link step.
  This is a deliberate friction cost paid for takeover resistance.
- Tenants migrating IdPs must re-link; a documented migration path is outstanding work.
- Support cannot "merge accounts" ad hoc — basis 3 must be specified before it is used.

## Security/data implications

- Closes the email-collision takeover class (P2-T045).
- `subject` is confidential and correlatable; it is classified under ADR-0019.
- Tombstones must survive Principal deletion so a subject is never silently reassigned.

- `tests/unit/test_idp_bridge.py` — `test_P2_T045_email_match_alone_cannot_link_an_account`,

- BOPEN-IDP-001 §6.1, §11; INV-P2-011, INV-P2-012.

## Supersedes / superseded by

Supersedes nothing. Constrains any future account-merge or identity-migration ADR.
